# Testing the SYNAPSE API with Postman

A ready-to-import Postman collection covering **every REST endpoint** in the
platform — generated straight from `backend/routes/api.php`, so it cannot drift
out of date.

| | |
| --- | --- |
| `SYNAPSE-API.postman_collection.json` | 181 requests, grouped by the role that may call them |
| `SYNAPSE-Local.postman_environment.json` | `base_url = http://localhost:8000` (your `php artisan serve`) |
| `SYNAPSE-Mock.postman_environment.json` | `base_url = http://127.0.0.1:8099` (the bundled contract stub) |
| `mock-server.js` | zero-dependency Node stub, for running the collection with no PHP/MySQL |
| `reports/newman-mock-run.txt` | the last full Newman run against that stub |
| `../../images/postman/` | the screenshots below |

Everything here is regenerated by two scripts in `tools/`:

```bash
python3 tools/generate_postman_collection.py     # collection + environments
python3 tools/render_postman_screenshots.py      # docs/images/postman/*.png
```

---

## 1. Import the collection

Postman ▸ **Import** ▸ select *both* `SYNAPSE-API.postman_collection.json` and
`SYNAPSE-Local.postman_environment.json`, then pick **SYNAPSE · Local** in the
environment dropdown (top right).

![The imported collection](../../images/postman/01-collection-imported.png)

The folders are the role groups from `routes/api.php`, so the collection doubles
as an authorisation matrix: running the *School Administrator* folder with a
student's token must return 403 on every request.

## 2. Log in — and let the test script capture the token

Open **00 · Public ▸ login**. The body is pre-filled from `LoginRequest`'s
validation rules (`email`, `password`) and the demo seed credentials.

![POST /api/login returns 200 and a Sanctum token](../../images/postman/02-login-request-200.png)

The **Tests** tab is where the automation lives. It asserts the response *and*
chains the token forward, so nothing is ever copy-pasted between requests:

```javascript
pm.test('Returns a bearer token', () => {
    const body = pm.response.json();
    pm.expect(body.token).to.be.a('string').and.to.have.lengthOf.above(20);
});

const body = pm.response.json();
pm.collectionVariables.set('token', body.token);
pm.collectionVariables.set('user_id', body.user.id);
pm.collectionVariables.set('school_id', body.user.school.id);
```

Send it and the assertions are reported per request:

![Test results for the login request](../../images/postman/03-login-tests-and-results.png)

> **Gotcha worth knowing:** `token` is *not* an environment variable on purpose.
> Environment scope resolves before collection scope in Postman, so an empty
> `token` in the environment would shadow the value the test script just wrote
> and every subsequent request would silently go out unauthenticated.

![The environment holds the base URL and the seed ids](../../images/postman/04-environment-variables.png)

## 3. Authenticated requests

Every other request inherits **Bearer `{{token}}`** from the collection. Change
`{{student_id}}`, `{{class_id}}` … to match what your `php artisan db:seed`
produced, or let the `store` requests write them for you (`Id is available for
the next request`).

| --- | --- |

## 4. Test the unhappy paths — they are the point

A happy-path collection proves very little. These three are the ones that catch
regressions:

**Validation (422).** Post a student with an email or matricule that already
exists. Laravel answers 422 and names every invalid field; the test asserts the
error keys, not just the status.

![422 with per-field errors](../../images/postman/07-validation-error-422.png)

**Missing token (401).** `Auth ▸ user` and `Auth ▸ logout` are pinned to
**No Auth** — they override the inherited bearer token on purpose, and they are
expected to come back 401. If they ever return 200, authentication is broken.

![401 without a token](../../images/postman/08-unauthorized-401.png)

**Read-only data (200).** The gradebook and the at-risk register return the
shapes the frontend renders, so they are asserted too:

![GET gradebook](../../images/postman/09-teacher-gradebook-200.png)
![GET at-risk register](../../images/postman/10-analytics-at-risk.png)

## 5. Run the whole thing

**In Postman:** open the collection ▸ **Run** ▸ pick the environment ▸ **Run
SYNAPSE API**. Roles are scoped per folder, so run one folder at a time unless
you are logged in as a super admin.

![Collection Runner results](../../images/postman/11-collection-runner-results.png)

**In CI / from a terminal** — same collection, headless:

```bash
# against the real backend
php artisan serve --host=127.0.0.1 --port=8000 &
newman run docs/postman/SYNAPSE-API.postman_collection.json \
       -e docs/postman/SYNAPSE-Local.postman_environment.json \
       --reporters cli,junit --reporter-junit-export build/newman.xml

# or against the bundled stub, with no PHP/MySQL installed
node docs/postman/mock-server.js &
newman run docs/postman/SYNAPSE-API.postman_collection.json \
       -e docs/postman/SYNAPSE-Mock.postman_environment.json
```

The last stub run: **181 requests, 616 assertions, 0 failures**
([full log](reports/newman-mock-run.txt)).

![Newman run](../../images/postman/12-newman-cli-run.png)

## Where the responses in the screenshots come from

The collection, URLs, headers, bodies, expected status codes and test scripts
are all **generated from the source**: `generate_postman_collection.py` reads
`routes/api.php`, resolves each route to its controller method, reads the
`FormRequest` that validates it to build the example body, and reads the
controller method to work out which status code it returns (`201` for a create,
`200` for an action, `202` for queued work). Re-run it after changing routes.

`mock-server.js` is a **contract stub, not the API**: it answers with the same
JSON shapes so the collection is runnable without PHP/MySQL, and implements only
the behaviours worth asserting (401 without a token, 422 on duplicate email or
matricule). It does not implement tenant isolation, subscription gating, plan
limits, at-risk maths or PDF rendering — test those against the real backend.
